# Fakit 하위 페이지와 사용 경험 설계

작성 기준: 2026-10-31. 사용자의 역할 분담과 현재 저장소 구현을 기준으로 한 제안이다. 사용자 조사 결과를 얻었다고 가정하지 않는다.

## 역할의 경계

- 효진(C): 이미지 모델 성능 개선, 테스트 이미지 확장, 평가 데이터 및 모델 버전 제공.
- 두현(D): 글 또는 영상 등 연관 모델 개발. 어느 형식을 지원할지와 모델의 입출력 계약 확정.
- 웹 담당: 모델이 내놓는 결과를 사용자가 이해하고 활용할 수 있는 화면, 설명, 오류 회복, 기록, 접근성, 로그인·확장 프로그램 연결. 모델의 성능 수치를 직접 만들거나 근거 영역을 임의로 그리지 않는다.

웹 담당의 산출물은 ‘페이지 수’보다 다음 질문으로 평가한다.
1. 사용자가 어떤 파일을 넣어도 되는지 알 수 있는가?
2. 결과 숫자를 정답률로 오해하지 않는가?
3. 분석 실패 후 다음 행동을 스스로 선택할 수 있는가?
4. 사진과 기록이 어디에 남는지 알 수 있는가?

## 1. 하나의 입력창, 종류별 결과 화면

### 현재 반영

- 글·영상·이미지 메뉴와 미작동 입력 페이지를 제거하고 ‘파일 탐지’로 통합.
- MIME과 확장자를 함께 확인해 이미지·영상·글/문서 유형을 구분한다. 확장자만으로 파일의 진위를 보장하지 않는다. 실제 이미지 디코딩도 별도로 성공해야 한다.
- 현재 지원하는 이미지 형식만 분석한다. 영상·글/문서에는 종류와 미지원 상태를 알려 준다. 혼합 업로드에서는 지원되는 이미지는 처리하고 나머지는 안내한다.
- 기존 `#/text`, `#/video` 링크는 통합 입력 화면으로 이동한다.
- 글을 붙여넣은 경우 ‘이미지가 없다’ 대신 글 분석 미지원 상태를 안내한다.

### 두현의 모델이 준비되면

- 사용자는 계속 같은 입력창을 쓴다. 파일마다 ‘이미지 / 영상 / 글’ 종류 칩과 처리 상태를 표시한다.
- 글 붙여넣기는 같은 작업 영역에 확장 입력창으로 제공한다. 별도의 탐지 페이지를 만들 필요는 없다.
- PDF·DOCX는 글 자체가 아니라 컨테이너다. 텍스트 추출, 스캔 문서 OCR, 포함 이미지 처리 중 무엇을 지원할지 따로 정한다. PDF를 이미지 모델에 무조건 넣지 않는다.
- 영상은 파일 확인 → 디코딩 → 프레임 추출 → 프레임 분석 → 요약으로 진행한다. 실제 단계 이벤트가 있을 때만 화면에 표시한다.
- 파일을 자동 분류해도 결과 표현은 달라야 한다. 이미지의 단일 점수, 글의 문단별 결과, 영상의 타임라인을 같은 막대 하나로 표현하지 않는다. 문단·프레임별 출력이 없는 모델에는 해당 UI를 제공하지 않는다.
- 미지원, 손상, 용량 초과, 암호화 문서는 ‘AI 판정’으로 처리하지 않는다.

## 2. 결과 읽는 법 — 최우선

사용자 질문: ‘AI 70%인데 왜 REAL이지?’, ‘이 사진이 가짜라는 증거인가?’, ‘다시 검사하면 달라지나?’

### 현재 반영

- `#/results` 페이지와 결과 상세창의 바로가기.
- REAL/AI가 모델 분류이며 출처나 진위를 입증하지 않는다는 설명.
- REAL 출력 기준선이 0.24라는 점과 `REAL 0.30 / AI 0.70 → REAL`이라는 명시적인 예제.
- 개별 결과 점수를 테스트 정확도나 검증된 신뢰도로 표현하지 않음.
- 얼굴 외 이미지, 재압축, 필터, 새 생성기에 대한 한계와 원본/출처 재확인 행동.
- 현재 웹 모델이 제공하지 않는 영역 표시·생성기 식별·생성 시각 등을 구분.

### 다음 개선

결과 상세에는 업로드 이미지, 분류, 원래 점수, 기준선, 모델 버전, 분석 시각을 한 화면에 묶는다. 점수 스케일에는 AI/REAL 방향과 기준선 위치를 함께 표시한다. ‘신뢰도 높음’ 같은 등급은 보정/검증 근거 없이 추가하지 않는다.

‘예상과 다른 결과’ 버튼을 결과 옆에 배치하는 것이 좋다. 입력 항목은 사용자가 알고 있는 출처(직접 촬영 / 생성 도구 / 모름), 원본·편집본 여부, 예상 분류, 선택 메모다. ‘모름’을 허용해야 오답 신고를 억지 라벨로 만들지 않는다.

이 피드백은 곧바로 정답 데이터가 아니다. 효진이 검토하고, 학습과 평가 중 어느 용도로 쓰는지 분리해야 한다. 제출 서버가 없을 때는 전송된 것처럼 성공 메시지를 보여주지 않는다.

확인할 사용성: 사용자가 결과를 보고 ‘이 파일이 AI라는 사실이 확정됐다’고 말하는지, 기준선 예제를 올바르게 설명하는지, 추가 확인 방법을 찾는지.

## 3. 사용 방법과 문제 해결 — 사용 중 이탈 줄이기

현재 `#/guide`에 파일 입력 방법과 문제별 해결 안내를 추가했다.

| 상황 | 화면에서 말할 것 | 다음 행동 |
| --- | --- | --- |
| 모델 로딩이 오래 걸림 | 처음에는 약 41MB 다운로드 및 준비가 필요함; 분석 진행과 구분 | 연결 확인, 준비 상태 확인 |
| 링크 불러오기 실패 | 원본 사이트 접근 제한·로그인 필요·잘못된 주소 가능 | 이미지 파일로 저장 후 업로드 |
| HEIC/GIF 미지원 | 지원 확장자와 단순 이름 변경이 변환이 아니라는 점 | JPG/PNG/WEBP로 내보내기 |
| 일부 파일 실패 | 성공/실패/대기 수를 구분하고 파일별 사유 제공 | 실패 파일만 재선택 |
| 붙여넣기 거부 | 브라우저 권한·복사한 내용의 종류 확인 | 키보드 붙여넣기 또는 파일 선택 |
| 로그인 미설정 | 로그인 없이 되는 범위 안내 | 분석 계속 |

다음 구현은 ‘다시 시도’ 버튼, 실패 파일별 원인, 중복 파일 감지, 실패한 파일만 재시도 순서가 적합하다. 무조건 새로고침하게 하면 성공한 결과도 잃을 수 있다. 모델 재로딩과 파일 재시도를 구분한다.

지원 환경 표는 직접 테스트한 브라우저/OS/기기만 적는다. ‘모든 브라우저 지원’이라는 문구는 쓰지 않는다. 모바일에서는 파일 선택과 카메라/사진 라이브러리 접근의 실제 동작을 확인한 뒤 안내한다.

확인할 사용성: 처음 오는 사람이 설명 없이 첫 분석을 완료하는지, 실패 문구를 본 뒤 도움 없이 복구하는지, 몇 번 같은 오류를 반복하는지.

## 4. 기록 — 다시 찾고 비교하는 목적

현재 기능: 기기 내 최대 200건, 축소 이미지·파일명·결과·기준선·시각, 분류 필터, 개별/전체 삭제, 이후 기록 저장 끄기.

### 다음 개선 순서

1. 파일명 검색과 날짜 필터. 사진이 많아도 ‘아까 본 파일’을 찾게 한다.
2. 원본/편집본 2개 비교. 선택한 파일의 이미지와 점수, 기준선, 모델 버전을 나란히 둔다. 어느 쪽이 더 진짜라는 결론을 자동 생성하지 않는다.
3. 분석 조건 묶음. 같은 파일을 다른 모델로 분석했을 때 결과가 달라졌음을 식별하도록 버전과 전처리를 남긴다. 이전 기록에 버전이 없다면 ‘버전 정보 없음’으로 표시한다.
4. 내보내기. 파일명·분류·점수·기준선·모델 버전·분석 시각을 CSV로 내보내고, 원본 사진은 기본 포함하지 않는다. 외부 공유 문서에는 결과의 한계를 함께 표시한다.

삭제 전에는 삭제 범위를 명확히 알린다. ‘저장 끄기’와 ‘기존 기록 삭제’는 다른 행동이다. 계정 동기화가 생기기 전에는 ‘내 계정의 기록’이라고 부르지 않는다.

확인할 사용성: 사용자가 찾으려는 기록을 찾는 데 걸리는 시간, 검색 실패, 삭제 범위 오해, 다른 기기에도 기록이 있을 것이라는 오해.

## 5. 사진과 기록 관리 — 사용자 통제

현재 `#/privacy`에 다음을 구분해 반영했다.

- 업로드 원본: 브라우저에서 분석하며 Fakit 서버에 업로드하지 않음.
- 로컬 기록: 축소 이미지에도 얼굴 등 개인을 식별할 수 있는 정보가 남을 수 있음.
- 외부 요청: 모델·라이브러리·글꼴 다운로드, 이미지 URL을 가져올 때 원본 호스트 요청.
- 로그인: 계정 식별자/표시 이름과 세션. 이미지 기록과 별개이며 로그아웃 후에도 기기 기록이 남음.
- 확장 프로그램: 선택한 이미지 URL 전달. 페이지 전체를 수집하지 않음.

이는 구현 설명 페이지이며 법률 검토를 거친 개인정보처리방침을 대신하지 않는다. 배포 시 운영 주체, 문의처, 실제 인프라 로그/보유 정책은 확인해서 보완한다.

추가하면 좋은 기능: 공용 기기용 기록 저장 끄기 바로가기, 로그인 상태와 별개인 저장 상태 표시, 삭제 직후 로컬 저장소까지 지워졌는지 확인. ‘안전하다’는 추상적인 문구보다 사용자가 직접 설정할 수 있는 항목이 중요하다.

## 6. 모델 정보 — 효진의 연구 결과를 사용자에게 전달

모델 상세는 메인 광고 지표가 아니라 업데이트를 확인하는 페이지로 만든다. 현재 페이지의 97.8%·99.8%는 기존 자료의 수치다. 새로운 평가 근거가 전달되기 전 임의로 갱신하거나 범용 정확도로 확대 해석하지 않는다.

효진에게 받을 항목:
- 모델 ID/버전, 배포일, 가중치/설정 식별자.
- 지원 이미지 범위, 출력이 어느 클래스의 점수인지, 판정 기준선과 선택 방법.
- 테스트셋별 샘플 수, 실제/생성 비율, 출처와 생성기, 중복/학습 데이터 겹침 처리.
- 실제를 AI로 잘못 분류한 비율, AI를 실제로 놓친 비율, 전체 Accuracy/F1/AUC 등.
- 압축·리사이즈·스크린샷·보정 등 조건별 결과. 확인하지 않은 조건은 ‘미측정’.
- 이전 버전 대비 달라진 점, 개선되지 않은 조건, 회귀한 조건.

웹에서는 ‘무엇이 좋아졌는가 / 어디서 실패하는가 / 내 파일에 적용되는가’를 먼저 보여주고, 아키텍처·학습률·레이어명은 펼쳐보기에 둔다. 테스트 이미지 갤러리는 출처·사용 권한·정답 라벨 근거가 확인된 것만 사용한다. 실패 사례도 같은 기준으로 싣는다.

## 7. 모션과 조형성의 기준

이번 수정에서는 회전 구체, 영문 슬로건, 반복되는 3단계 홍보 문구를 제거했다. 실제 업로드 이미지가 시각 구성의 중심이다.

현재 구현: 원본 비율을 유지한 이미지 면 → 실제 256×256 입력 면 → 판정 점수와 기준선. 원본과 입력의 차이를 바로 비교할 수 있고, 실제 처리 상태에 따라 입력 프레임이 강조된다. 결과 점 위치는 모델 출력값으로 정해진다. 임의의 650ms 분석 지연과 사진 위 스캔선을 제거했다.

다음 디자인에서 가능한 모션:
- 드래그가 들어오면 입력 영역 경계만 반응: 놓을 수 있는 위치 안내.
- 원본/모델 입력 전환: 비율 변화와 리사이즈를 보여 줌. 원본을 덮어쓰지 않음.
- 완료 시 결과 카드 배치 전환: 선택한 파일과 결과의 연결 유지.
- 두 이미지 비교 시 동일한 확대/이동: 차이를 살펴보는 조작.
- 영상 모델이 생기면 실제 추출 프레임만 타임라인에 차례로 등장.

하지 않을 것: 증거 없는 얼굴 랜드마크·열지도, 처리와 무관한 빛 스캔, 임의의 진행률, 실제 속도를 늦춘 연출. 모델 출력에 없는 부위별 근거는 Spline으로도 만들어 넣지 않는다. Spline을 쓸 경우에도 입력·상태·결과에 연결할 수 있는 장면에 한정한다.

## 8. 사용 만족도 확인 — 아직 조사되지 않은 가설

초기에는 소수의 실제 사용자를 관찰하는 정성 테스트로 시작한다. 예를 들어 5명 정도를 대상으로 아래 과제를 주고, 사용자가 막히는 지점을 적는다. 그 인원으로 통계적 일반화를 주장하지 않는다.

| 과제 | 관찰할 것 | 끝나고 물을 것 |
| --- | --- | --- |
| 처음 방문해 얼굴 사진 1장 검사 | 첫 성공까지의 행동, 버튼을 못 찾는 위치 | ‘어디서 시작해야 할지 분명했나요?’ |
| 이미지와 영상 함께 넣기 | 자동 분류와 미지원 상태 이해 | ‘어떤 파일이 처리됐다고 생각하나요?’ |
| 기준선 예제 해석 | 숫자를 정답률로 착각하는지 | ‘REAL 0.30인데 REAL 분류인 이유는?’ |
| 막힌 이미지 URL 가져오기 | 오류 후 복구 성공 여부 | ‘다음에 무엇을 해야 할지 알았나요?’ |
| 기록 찾기·저장 끄기 | 기존 기록과 이후 저장의 차이 이해 | ‘어떤 정보가 어디에 남아 있나요?’ |

과제 직후 쉬움 정도(예: 1~5)와 이유를 함께 묻는다. 전체 만족도 하나만 묻지 말고 입력 편의·대기 이해·결과 이해·실패 복구·저장 통제를 구분한다. 점수 개선 목표는 최초 측정 이후 정한다.

서비스 이벤트를 수집한다면 파일 선택→허용→시작→완료/실패, 오류 유형, 결과 도움말 열기 정도로 최소화한다. 파일명·이미지·원문·전체 URL을 분석 로그에 넣지 않는다. 현재는 이 계측이나 피드백 전송을 구현하지 않았다.

## 작업 순서

1. 이번 반영: 통합 입력, 장식 삭제, 실제 입력/결과 과정, 결과 읽기, 문제 해결, 기록·사진 관리.
2. 다음 웹 작업: 파일별 재시도와 오류, 기록 검색·비교, 버전 표시, 결과 피드백 저장 경로.
3. 효진 산출물 수령 후: 모델 업데이트/조건별 평가/검증된 예제 갤러리.
4. 두현 산출물 수령 후: 자동 분기 확장, 해당 형식의 입력 검증과 결과 UI, 사용자 테스트.

두현과 먼저 합의할 것: 지원 형식·크기·길이, 언어/영상 조건, 입력 데이터 구조, 전처리 주체, 브라우저/서버 실행 위치, 응답 스키마, 실패 코드, 모델 버전, 부분 결과·취소 가능 여부. API 계약이 정해지기 전에는 ‘5,000자’나 ‘MOV 지원’ 같은 제한을 임의로 확정하지 않는다.
